## Project Overview

**KeyServ** — a Chilean services marketplace platform with biometric authentication (fingerprint + facial recognition). Built as a thesis project by a team (Felipe, OmaryLuis, luchoo23); the thesis has since been delivered and the project is being treated as a commercial product going forward.

## Active Project

There are three Django project variants (`codigo/viejo/ProyectoDjango/`, `codigo/viejo/ProyectoKeyServ/`, `codigo/backend/django/`). **`codigo/backend/django/` is the canonical, most complete version** (formerly `Tesis/`) and should be the default target for all work.

**Database engine changed in Fase 3: PostgreSQL, not MySQL.** The thesis's "MySQL + AWS" restriction only applied to the academic deliverable — the user confirmed it doesn't bind the commercial product going forward. See `docs/RECOMMENDED_ARCHITECTURE.md` for the reasoning.

**Frontend migration in progress (current branch `api-ionic-migration`):** the product is moving from Django server-rendered templates to an Ionic/Angular app (`codigo/frontend/ionic/`) talking to a new DRF REST API (`KeyServApp/api/`). The two frontends coexist during the migration — template views are retired area by area, not all at once. **Full phased plan: `docs/PLAN_MIGRACION_IONIC.md`.** See "API + Ionic migration" under Architecture below for the technical design so far.

### Environment Setup

```powershell

python -m venv venv_tesis

# Activate virtual environment (Python 3.14 / Windows)

# Install dependencies (requirements.txt exists as of Fase 3)
pip install -r requirements.txt

# .env already exists at codigo/backend/django/.env (gitignored) — to recreate from scratch:
Copy-Item .env.example codigo\backend\django\.env
```

`venv_tesis` has **Django==5.2.16** (upgraded from 4.2.1 in Fase 4 — see below), django-environ, psycopg2-binary, and Pillow installed and verified (`manage.py check`/`makemigrations`/`migrate`/`test` all run clean). **`opencv-python`/`face_recognition`/`dlib` are now installed too** (see Known Issues for the toolchain/version story); `fpdf2` is still not installed in this environment — it's only needed to exercise `GUARDAR_DOCUMENTO.py`, which is legacy/broken anyway (see Known Issues).

**Why Django 5.2 and not 4.2.1** (the version the thesis originally used): Django 4.2's template `Context.__copy__` is incompatible with Python 3.14's `copy.copy()` — every `manage.py test` request that renders a template crashes with `AttributeError: 'super' object has no attribute 'dicts'`. Tried the latest 4.2 LTS patch (4.2.30) first — still broken. 5.2 LTS fixes it cleanly; no application code needed to change. The user explicitly said feel free to change Django/Python versions if it makes things run better/more compatible — don't treat 4.2.1 as sacred. See `docs/FASE4_LOG.md`.

### E2E tests (Playwright, Fase 7 — real browser against the real app)

```powershell
cd codigo/frontend/ionic
npx playwright install chromium   # una vez — descarga el binario de Chromium que usa Playwright
npm run test:e2e                   # corre e2e/*.spec.ts contra la app real
npm run test:e2e:ui                # mismo suite, con el UI mode de Playwright (ver cada paso/trace)
```

A diferencia de `npm test` (Karma/Jasmine, `HttpClient` mockeado con `HttpClientTestingModule`, no habla con ningún backend real), estos tests corren contra la app de verdad: un Chromium real clickea el Ionic servido (`ng serve`, `:8100`) que a su vez habla con la API Django real (`:8000`, Postgres real, datos demo reales vía `sembrar_datos_demo`). **Requiere el backend ya corriendo** (`manage.py runserver 8000`, con migraciones + datos demo aplicados) — `playwright.config.ts` solo levanta el frontend él mismo (`npm start`, reusa uno ya corriendo si existe vía `reuseExistingServer`), no el backend. Los tests deliberadamente no tocan transiciones de estado de una contratación (confirmar/completar/pagar/valorar) — la data demo sembrada trae un ejemplo de cada estado del BPMN a propósito para el portafolio, y una transición real la rompería; sí prueban mandar un mensaje de chat (agrega una fila, no cambia ningún estado). Cubre: login (real y con credenciales incorrectas), guard de rutas protegidas, catálogo público (listado/búsqueda/detalle) y el chat de una contratación (mandar un mensaje de texto y verlo aparecer como burbuja, contra el rediseño de Fase 7). **Alcance solo web por ahora** — Appium (E2E nativo Android/iOS) quedó deliberadamente fuera, decisión explícita del usuario, para una sesión aparte.

### Continuous Integration

`.github/workflows/tests.yml` runs on every push to `master`/`api-ionic-migration` and every PR into `master`: a `backend` job (Postgres 17 service container, `pip install -r requirements-ci.txt` then `manage.py test KeyServApp`), a `frontend` job (`npm ci` then `ng test --watch=false --browsers=ChromeHeadlessCI`), and an `e2e` job (its own Postgres service, migrates + seeds real demo data, starts `manage.py runserver` in the background, waits for it to respond, then `npx playwright install --with-deps chromium` + `npx playwright test` — uploads the HTML report as a build artifact only if something fails). **`requirements-ci.txt` is a deliberate subset of `requirements.txt`** — it skips `dlib-bin`/`opencv-python`/`face_recognition`/`transbank-sdk`, since CI tests mock those or never exercise them for real (see "Known Issues" for why those packages are heavy to install).

See "API + Ionic migration" under Architecture → Data Flow below for what's actually built (Fases 1-4 done, Fase 5 in progress — this Commands section only covers running things, not what exists).

**API + Ionic migration (in progress, branch `api-ionic-migration`):** the product is moving off server-rendered Django templates onto an Ionic/Angular frontend (`codigo/frontend/ionic/`, Ionic + Angular + Capacitor for a single codebase across web/Android/iOS) speaking to a new DRF REST API mounted at `/api/` (`KeyServApp/api/`, wired in `KeyServProject/urls.py`). **See `docs/PLAN_MIGRACION_IONIC.md` for the full phased plan, stack rationale, and what deliberately stays on Django (the admin/moderation panel) — that doc is the source of truth for phase numbers, not this file.** The two frontends are meant to coexist for several phases — template views get retired area by area as the Ionic app grows, following a strangler-fig approach (never a big-bang cutover). Design points worth knowing before extending it:
- **Auth is a hand-rolled JWT scheme (PyJWT), not `djangorestframework-simplejwt`.** `Usuario` is not `AUTH_USER_MODEL` (a Fase 3 decision, see `decorators.py`) and simplejwt assumes `get_user_model()` in several places, so it doesn't fit cleanly. `api/jwt_utils.py` issues a short-lived stateless JWT access token (`settings.JWT_ACCESS_TOKEN_MINUTOS`, default 20 min) plus an opaque high-entropy refresh token whose *hash only* is persisted in the new `TokenSesion` model (one row per device/login, not per `Usuario`) — this keeps the refresh side revocable (real logout, "log out everywhere", a planned future "trusted device" flow for the biometric lock) despite the access token itself being stateless. `api/authentication.py`'s `JWTAuthentication` (registered as DRF's default in `REST_FRAMEWORK['DEFAULT_AUTHENTICATION_CLASSES']`) reads `Authorization: Bearer <access token>`, sets `request.user` to the matching `Usuario`, and returns 401 rather than redirecting to `/sesion/` like `login_requerido` does for template views. `Usuario` gained fixed `is_authenticated`/`is_anonymous` properties (always `True`/`False`) purely so it satisfies DRF's `IsAuthenticated` check, which expects those attributes.
- **API views deliberately reuse `views.py`'s security helpers instead of reimplementing them** — `api/views.py`'s `LoginView` imports `_clave_intentos_login`/`_registrar_intento_sospechoso`/`MAX_INTENTOS_LOGIN` straight from the template-based `views.py` so the (IP, email) brute-force lockout and `IntentoAccesoSospechoso` logging stay in exactly one place instead of two implementations that could drift.
- **CORS** (`django-cors-headers`) is scoped to `/api/*` only via `CORS_ALLOWED_ORIGINS` (env var, defaults to `http://localhost:8100`, which is why the Ionic `npm start` script pins `ng serve --port 8100` instead of Angular's default 4200) — the template/`/admin/` site stays same-origin and untouched by this.
- **`drf-spectacular`** auto-generates the OpenAPI schema (`/api/schema/`) and a Swagger UI (`/api/docs/`); the schema is intended to drive a generated TypeScript client for the Ionic side, though that generation step isn't set up yet.
- **Tokens are stored via `capacitor-secure-storage-plugin` (Keychain on iOS, Android Keystore-backed `EncryptedSharedPreferences` on native Android) as of Fase 7 "Hardening"** — `core/almacenamiento-seguro.ts` (`AlmacenamientoSeguro`) wraps the plugin; `Auth` (`core/auth.ts`) keeps an in-memory copy of the tokens for the synchronous reads `authGuard`/`authInterceptor` need, populated once at startup via `Auth.inicializar()` wired as an `APP_INITIALIZER` in `app.module.ts` (Angular doesn't finish bootstrapping — no guard can run — until that async load from secure storage completes). On a browser build (not native) the plugin itself falls back to `localStorage`, unencrypted — there's no browser equivalent of Keychain/Keystore, a limitation of that environment rather than something the app code can fix. **Verified against a real native Android build**, not just web: login → force-stop the process (a real app-close, not just reloading a tab) → relaunch → session was still active, confirming the token survived in the real on-device Keystore rather than only in process memory. See `docs/BACKLOG.md`'s Fase 7 section and `docs/PLAN_MIGRACION_IONIC.md`'s "Nota de seguridad" for the full writeup.
- **`PublicacionListView`/`PublicacionDetailView` (`api/views.py`) are `AllowAny`, overriding the `IsAuthenticated` default** — the catalog is public on purpose (confirmed with the user), same as `/servicios/`. `PublicacionListView.get_queryset()` duplicates `catalogo_view`'s filter logic (search/region/rating/order) rather than sharing it, because the search half needs `Unaccent` (imported straight from `views.py`, not reimplemented) applied through DRF's query-param parsing instead of Django's `request.GET`; pagination is DRF's `PageNumberPagination` (`page_size=20`, matching `PUBLICACIONES_POR_PAGINA` — duplicated on purpose, see the comment on `PaginacionPublicaciones`, since sharing the actual class would couple the template catalog to DRF). `PublicacionDetailView` intentionally does **not** filter by `estado_moderacion`, matching `publicacion_detalle_view`'s existing (slightly odd) behavior of not 404ing an unapproved publication reached by direct link.
- **`RegistroView` (`POST /api/auth/registro/`) reuses `RegistroForm` (forms.py) directly instead of a parallel DRF serializer.** A plain `django.forms.Form` accepts a plain dict (`request.data`) as its data just fine — it doesn't need a real `QueryDict` — so `RegistroForm(request.data)` works with no adapter. This keeps registration validation (RUT/age/email-uniqueness/password rules) in exactly one place instead of two that could drift, same reasoning as `LoginView` reusing the login-attempt lockout. Trade-off: `drf-spectacular` can't introspect a `Form`'s fields, so `/api/schema/` won't document this endpoint's body — acceptable since nothing generates a TypeScript client from that schema yet. No auto-login after registering, matching `register_view`'s existing "account created, now log in" behavior; unlike `register_view`, it does **not** reject an already-authenticated caller — that check exists on the template side to avoid confusing session/cookie state, which doesn't apply to a stateless JWT client.
- **`RecuperarView`/`RecuperarConfirmarView` (`POST /api/auth/recuperar/`, `GET`/`POST /api/auth/recuperar/confirmar/<token>/`) reuse `RecuperarForm`/`NuevaPasswordForm` and the signed-token helpers (`_generar_token_recuperacion`/`_usuario_desde_token_recuperacion`, `django.core.signing`) from `views.py` unchanged, same rate-limit and same "same message whether or not the account exists" behavior.** The one real difference from the template: the reset link in the email points at `settings.IONIC_FRONTEND_URL` (new env var, defaults to `http://localhost:8100`), not a Django URL — whoever calls this endpoint is the Ionic client, so step 2 has to resolve there too. `GET` on the confirm endpoint only validates the token (so the Ionic screen can show "link expired" before the person fills out a new password in vain) and returns no user data — the token itself is already sensitive enough without echoing back whose it is.
- **`PerfilView` (`PUT /api/auth/perfil/`) reuses `EditarPerfilForm` (a `ModelForm`) the same way `RegistroView` reuses `RegistroForm`**, including its email-uniqueness-excluding-self check and its `foto_perfil` handling (an optional `ImageField` — DRF's default parsers already include `MultiPartParser`, so `request.FILES` is populated for free when the Ionic client sends `multipart/form-data`; if no new file is sent, the `ModelForm` leaves the existing photo untouched, same as the template path). `UsuarioMeSerializer` gained `comuna` (the raw FK pk) and a `region` `SerializerMethodField` (derived from `comuna.region_id`) purely so the Ionic edit-profile screen can prefill its region→comuna cascade from one `GET /api/auth/me/` call instead of a second round-trip.
- **`ProveedorSerializer` (nested proveedor info on a publication) uses `SerializerMethodField`s, not `source='ranking.puntuacion_promedio'` + `default=...`.** The latter was tried first and is the more "idiomatic DRF" way to handle an optional related object, but a real bug surfaced in `tests_api.py` (`test_listado_incluye_proveedor_embebido`): the declared `default=0` on `total_valoraciones` silently did not apply, returning `None` instead of `0`, while the sibling field's `default=None` happened to look correct by coincidence. Switched to explicit `get_puntuacion_promedio`/`get_total_valoraciones` methods with `getattr(usuario, 'ranking', None)` instead — easier to verify, no reliance on DRF's read-path default-application semantics for dotted `source` chains.
- **`PerfilProveedorView` (`PUT /api/auth/perfil-proveedor/`) reuses `CrearPerfilForm` the same way `PerfilView` reuses `EditarPerfilForm`**, including the fusion of checkbox `areas_servicio` + free-text `otra_area_servicio` into one comma-joined string. Certificates/documents aren't a Form field (same reason as `PublicacionForm`: Django has no multi-file `FileField`) — they come from `request.FILES.getlist('documentos')`, same `MAX_DOCUMENTOS_PUBLICACION` cap and same "No firmado" (`pk=2`) initial `estado_documento` as `crear_perfil_view`. Files that fail `validators.py` (extension/byte-signature/Pillow decode) don't 400 the whole request — they're listed in the response's `documentos_rechazados`, matching the template's "reject the bad ones, save the rest" behavior. `DocumentoPerfilListView`/`DocumentoPerfilEliminarView` are new equivalents of the list/delete half of `crearperfil.html` (own documents only, 404 not 403 for someone else's, same as `documento_perfil_eliminar_view`). New public catalog `GET /api/catalogos/categorias/` (`CategoriasListView`, just returns `CATEGORIAS_PUBLICACION` from forms.py as a plain list) feeds the Ionic checkbox multi-select.
- **`PreferenciasView` (`PUT /api/auth/preferencias/`) and `CambiarPasswordView` (`POST /api/auth/cambiar-password/`) split `preferencias_cuenta_view`'s two independent template `<form>`s (distinguished there by a hidden `form` field) into two separate endpoints** — each is already its own request from a JSON API client, so there's no equivalent need for the hidden-field dispatch. Both reuse their forms unchanged (`PreferenciasCuentaForm`, `CambiarPasswordForm` — the latter still requires the current password before accepting a new one).
- **`ContratacionListCreateView`/`ContratacionDetailView` (`GET`/`POST /api/contrataciones/`, `GET /api/contrataciones/<id>/`) are equivalents of `reservas_view`/`contratacion_crear_view`/the non-chat half of `contratacion_detalle_view`.** `ContratacionDetailView` (and `ContratacionMensajesView` below) return 404 — not 403 — for a contratación the caller isn't part of, same reasoning as `documento_descargar_view`: don't confirm the resource exists to someone poking at IDs, and log the attempt via `_registrar_intento_sospechoso` same as the template.
- **`ContratacionMensajesView` (`GET`/`POST /api/contrataciones/<id>/mensajes/`) is the equivalent of the chat embedded in `contratacion_detalle_view`** — `GET` also marks `ultimo_leido`, same as the template. Reuses `MensajeForm` for the write side.
- **`ContratacionConfirmarView`/`ContratacionCompletarView` (`POST .../confirmar/`, `POST .../completar/`) reuse `ReautenticacionForm`/`MontoAcordadoForm` unchanged, plus the exact same (usuario, contratación) rate-limit helpers as the template (`vistas_legacy._reautenticacion_bloqueada`/`_registrar_intento_reautenticacion`, imported not reimplemented).** The one piece that couldn't be reused as-is: the optional `ItemPresupuesto` budget breakdown's row parser — `_parsear_items_presupuesto_api` (api/views.py) mirrors `_parsear_items_presupuesto`'s exact validation rules but reads a JSON list of objects (`request.data.get('items')`) instead of parallel `request.POST.getlist(...)` arrays, since that's how a JSON client naturally sends repeated rows. Not wired into the Ionic UI yet — `contratacion/detalle/detalle.page` only exposes the single `monto` field, not the itemized breakdown.
- **`ValoracionCrearView` (`POST /api/contrataciones/<id>/valoracion/`) reuses `ValoracionForm` and the same `validators.py` checks on attached photos as the rest of the site**, then calls `vistas_legacy._recalcular_ranking` (imported, not reimplemented). Rejected photos don't 400 the whole request — they're listed in `imagenes_rechazadas` while the review itself still saves, same `documentos_rechazados`-style tradeoff as `PerfilProveedorView`.
- **`PagoWebpayIniciarView`/`PagoWebpayConfirmarView` move the payment return leg from a Django URL to the Ionic app (`settings.IONIC_FRONTEND_URL`), same pattern as `RecuperarView`.** `PagoWebpayIniciarView` (`POST /api/contrataciones/<id>/pagos/webpay/iniciar/`) returns `{token, url_pago}` instead of rendering the template's auto-submit HTML page — the real POST of `token_ws` to Transbank (their protocol requires POST, a GET won't do) gets built client-side in Ionic instead (`contratacion/detalle/detalle.page.pagarConWebpay()`, a dynamically-created hidden `<form>`, same trick as the template just moved to the browser). `PagoWebpayConfirmarView` (`POST /api/pagos/webpay/confirmar/`, `AllowAny`) is where the new `pago/webpay/retorno` Ionic screen posts whatever query params Transbank's redirect gave it (`token_ws` or `TBK_TOKEN`) — unauthenticated on purpose, same as the template's `@csrf_exempt`-only view: Transbank redirects the user's browser here directly, not a request carrying our session/JWT, and the JWT may have gone stale during the time spent on Transbank's pages anyway. The real "credential" here is `token_ws` itself.
- **`PagoKhipuIniciarView`/`PagoKhipuEstadoView` are simpler than Webpay on the client side** — Khipu accepts a plain GET navigation, so `PagoKhipuIniciarView` (`POST /api/contrataciones/<id>/pagos/khipu/iniciar/`) just returns `{payment_url}` and Ionic navigates there with `window.location.href`, no `<form>` trick needed. `PagoKhipuEstadoView` (`GET /api/contrataciones/<id>/pagos/khipu/estado/`) is the equivalent of `pago_khipu_retorno_view`'s reconsult-on-return UX (re-checks Khipu if still `PENDIENTE`) for the new `pago/khipu/retorno/:id` screen — same as the template, the real source of truth stays the webhook (`pago_khipu_notificacion_view`, unchanged, still plain Django since Khipu calls it server-to-server and the browser is never involved).
- **`VerificarBiometriaNativaView` (`POST /api/auth/verificar-biometria-nativa/`) has no template-side equivalent to mirror — it's new in Fase 5, not a migration of an existing view.** Unlike `/rostro/`, where the server actually processes biometric data, Face ID/fingerprint verified via `@capgo/capacitor-native-biometric` happens entirely inside the phone's secure enclave — the server never sees it and structurally can't verify it directly. The endpoint just trusts an already-authenticated JWT session and sets `verificado_biometricamente = True`, a deliberate trust-model decision made with the user (same reasoning production banking-style apps use): the "credential" here is the device's own secure hardware, not something the server can independently check. No re-auth password required, unlike `ContratacionConfirmarView`/`CambiarPasswordView` — those protect a mutation the server can't otherwise verify happened correctly either, but this one's whole point is that the phone already did a stronger check than a password would.
- **`RostroEstadoView`/`RostroRegistrarView`/`RostroVerificarView` (`GET /api/auth/rostro/estado/`, `POST /api/auth/rostro/registrar/`, `POST /api/auth/rostro/verificar/`) are the API equivalents of `rostro_view`/`registro_rostro_view`/`verificacion_facial_view`.** `estado` just exposes `bool(request.user.encoding_facial)` (never the encoding itself) so `rostro.page` knows whether to default to "registrar" or "verificar" mode from one call, same as the template does server-side. `registrar`/`verificar` reuse `vistas_legacy._obtener_frames_captura(request)` unchanged (it only reads `request.FILES`, no session-specific logic) to pull the `rostro_frames` multipart burst, then call the same `biometria.calcular_encoding_facial`/`verificar_rostro_usuario` the template views call — same blink-liveness pipeline, same `probando_face_recognition.verificar_prueba_de_vida_parpadeo`, just a DRF response instead of a redirect+message. `KeyServApp/tests_api.py`'s `RostroApiTests` (9 tests) mirror `tests.py`'s `ReconocimientoFacialTests`, mocking `biometria.calcular_encoding_facial`/`verificar_rostro_usuario` at the same level.
- `KeyServApp/tests_api.py` is a separate test module from `tests.py` on purpose, for the duration of the migration, so template-view and API-view tests don't collide in one giant file — each API scenario mirrors an equivalent one already covered in `tests.py`'s `LoginViewTests`.
- The face-recognition biometric stack (`codigo/biometria/reconocimiento_facial/`, `KeyServApp/biometria.py`) was originally expected to stay in place only until a native biometric lock (via Capacitor) was built and verified on the Ionic side, at which point it and its dependencies (`opencv-python`/`face_recognition`/`dlib-bin`, see Known Issues) would get retired together. **That native biometric lock now exists and is verified** (`VerificarBiometriaNativaView` + `biometria.page`, above) — but instead of retiring the face-recognition stack, the user asked to extend it to Ionic too (as the fallback for devices without native Face ID/fingerprint, see the Phase 5 paragraph above and `RostroEstadoView`/etc. bullet). Retiring `codigo/biometria/reconocimiento_facial/`/`KeyServApp/biometria.py` is therefore no longer a natural next step — both the Django templates and the Ionic app (web + native) now depend on it.

**Facial recognition — single-capture blink liveness (2nd redesign):** `/rostro/` (`rostro_view`) shows a register-or-verify screen depending on whether `Usuario.encoding_facial` (migration `0024`, `JSONField`) is set. This has gone through two liveness designs: the original 1-photo compare had two real problems found via live webcam testing (a different person's photo could match by accident in low light, and the pipeline took whichever face it detected first instead of rejecting 0/multi-face photos); the first fix was a 3-photo head-turn sequence (front/right/left, validated via `cv2.solvePnP` yaw), which worked but proved tedious/slow to capture in practice. It's now a single guided capture instead: the browser records a ~2s burst of frames (`_captura_camara.html`, `getUserMedia`/`<canvas>`, still no manual file picker) while the user just looks at the camera and blinks once, submitted as a multi-file `rostro_frames` field. `registro_rostro_view` (`POST /rostro/registrar/`) and `verificacion_facial_view` (`POST /rostro/verificar/`) both call `biometria.calcular_encoding_facial`/`verificar_rostro_usuario`, which forward to `probando_face_recognition.verificar_prueba_de_vida_parpadeo(rutas_frames)`: it silently discards any frame without exactly one detected face (normal mid-blink/motion-blur noise), requires at least `FRAMES_MIN_PARPADEO` (8) usable frames, computes the Eye Aspect Ratio (`_ear_de_ojo`, standard Soukupová & Čech formula over the `left_eye`/`right_eye` landmarks `face_recognition` already provides) per frame, and confirms a real open→closed→open transition (`_hubo_parpadeo`) — a static photo/screen can't blink, so this replaces the head-turn as the anti-spoofing signal. Among frames passing that check, it picks the highest-EAR (most open-eyed) frame that also clears a brightness/blur gate (`_calidad_de_imagen_aceptable`, `BRILLO_MINIMO`/`NITIDEZ_MINIMA`) for the actual encoding — that quality gate plus a stricter comparison tolerance (`TOLERANCIA_COMPARACION = 0.5`, down from `face_recognition`'s 0.6 default) is what now targets the original low-light false-match problem directly, instead of relying on pose. `verificacion_facial_view` compares against `Usuario.encoding_facial` via `comparar_encodings` and sets the same `Usuario.verificado_biometricamente` flag the fingerprint flow uses (RF001 treats fingerprint/face/Clave Única as alternative methods, not all-required). For fast feedback, `rostro.html`'s JS immediately posts the whole burst to `POST /ajax/validar-captura-rostro/` (`validar_captura_rostro_ajax` → `biometria.calcular_encoding_facial`, result discarded) before enabling the form's submit button — the same encoding gets recomputed once more on the real submit, same "cheap to redo, not worth caching" pattern the old per-step AJAX endpoint used. `ReconocimientoFacialTests` mock `biometria.calcular_encoding_facial`/`verificar_rostro_usuario` at the view level; `PruebaDeVidaParpadeoTests` unit-tests `_hubo_parpadeo` directly against synthetic EAR sequences (pure Python, no image needed). The backend never opens a webcam itself — capture happens in the client's browser, matching how the fingerprint flow already worked. **Verified live end-to-end through the actual browser UI against a real webcam** (see Known Issues) — including a real first-attempt failure that's informative about the design: the capture ran cleanly (8+ usable frames, no crash) but no blink landed inside the ~2s window, so `validar_captura_rostro_ajax` correctly reported "no blink detected"; a second attempt caught a natural blink, passed, and the subsequent `POST /rostro/verificar/` matched against the stored reference encoding and set `verificado_biometricamente=True`, confirmed on `/perfil/`.

**Security hardening (Fase 6):** Every uploaded image/document passes through `validators.py` (extension whitelist + byte-signature check + a real Pillow decode, not just "Django could open it") before an optional `antivirus.py` ClamAV scan (off by default in this dev environment). `IntentoAccesoSospechoso` logs any attempt to reach a conversation/contract/document that isn't the requester's, or a brute-force lockout on login/re-authentication/fingerprint verification — including attempts from sessions with no logged-in user at all — with an approximate IP geolocation attached via a local DB-IP City Lite database (`geolocalizacion.py`, downloaded with `manage.py descargar_geoip`; degrades to `(None, None)` if the database isn't present or `GEOIP_HABILITADO=False`), surfaced as an alert in the admin dashboard (attribution footer required by DB-IP's CC-BY license). Identity documents (`Documento`) live in `storage.py`'s private `FileSystemStorage` (`base_url=None`, outside `MEDIA_ROOT`) and are only ever served through the authenticated `documento_descargar_view`. Other real fixes from the same pass: session IDs are cycled on login (session-fixation fix), login/re-auth are rate-limited per (user, action) via the cache, the minimum password length went from 6 to 8 chars reusing `AUTH_PASSWORD_VALIDATORS`, fingerprint verification used to accept a client-supplied file *path* as plain text and pass it straight to `Image.open()` (arbitrary file read) and now requires a real upload, and `/registro/`/`/sesion/` now reject an already-logged-in session instead of silently re-processing it. `SECURE_HSTS_*`/`SECURE_SSL_REDIRECT`/`SESSION_COOKIE_SECURE` activate automatically once `DEBUG=False`, and `/admin/`'s URL is configurable via an env var.

**Messaging (Fase 4, redesigned in Fase 5):** `Conversacion` is now 1:1 with a `Contratacion` ("chat per job") instead of 1:1 with a pair of users — previously messages from unrelated contracts between the same two people bled into a single thread. `chat_view`/`conversacion_detalle_view` list conversations and view/send messages, access restricted to participants (verified with a third "intruder" user in tests). **Admin & moderation (Fase 5, reorganized Fase 6, moderator scope narrowed Fase 7):** A native Django "Moderador" group (Groups/Permissions, not a custom role system — see `configurar_grupo_moderador.py`) can view/change publications, documents, ratings (`Valoracion`/`ValoracionImagen`), and derived support cases (`Consulta`), view the aggregate `Ranking`, and view suspicious-access alerts (`IntentoAccesoSospechoso`); it cannot see `Usuario`, payments, contracts/history (`Contratacion`/`HistorialEstadoContratacion`), private conversations/messages (`Conversacion`/`Mensaje`), or other sensitive/infrastructure tables — Django's admin simply omits models with no granted permission. This was deliberately narrowed from an earlier, broader "everything except logs and sensitive data" scope (which gave moderators visibility into the full contracting pipeline and private chats) after the user flagged that a moderator should only react to escalated cases and alerts, not monitor operational business data. `/admin/` has a custom `index.html` showing a pending-approvals dashboard (unmoderated publications + open incidents + suspicious-access alerts), laid out as a responsive KPI-card grid (`.ks-panel-grid` in `ks_admin_theme.css`) instead of stacked full-width blocks, after overriding Django's own `.dashboard #content { width: 600px }` rule that was wasting most of the available width next to the sidebar. `LogEntry` (Django's native audit log) is registered but restricted to `is_superuser`. Contract start timestamps are `readonly_fields` (visible, immutable) in the admin. Fase 6 replaced Django's default single flat "Keyservapp" block (~25 models in one undifferentiated list) with a task-based grouping — `admin.py` overrides `AdminSite.get_app_list` to bucket models into `_CATEGORIAS_ADMIN` (Solicitudes y moderación / Seguridad / Mensajería / Usuarios y cuentas / Catálogos de referencia / Finanzas e infraestructura / Auditoría; anything unclassified falls into an "Otros" catch-all instead of silently vanishing) without touching any model registration or permission — with the narrowed scope, a Moderador account now only sees "Solicitudes y moderación" and "Seguridad" (Mensajería/Contratación-related categories disappear on their own since Django's admin omits any category left with zero visible models).

**Support:** `/contacto/` now writes to the real `Consulta` model (part of the original thesis schema but unused until Fase 5) instead of being a static page; moderators triage these via `/admin/`.

**Payments (Fase 6):** Real integration, two methods chosen with the user (not Transbank alone — combination picked after researching Chilean gateways): **Webpay Plus** (`pagos.TransbankService`, `transbank-sdk`) for cards, and **Khipu** (`pagos.KhipuService`, plain `requests` — no third-party SDK, since Khipu's public docs had conflicting info on the exact auth scheme and a small in-house client keeps that a one-line fix if wrong) for direct bank transfer. `Publicaciones.precio` (new, migration `0018`) is only a starting reference — client and provider can agree on a different amount over chat before the provider confirms, so `Contratacion.monto_acordado` (new, migration `0020`, set in `contratacion_confirmar_view` from an optional `monto` field next to the re-auth password, defaulting to `publicacion.precio` if left blank or invalid) is what actually gets charged; `publicacion.precio` is never read again after confirmation. The `Pago` model (migration `0019`) tracks each attempt (`metodo`, `estado`: PENDIENTE/PAGADO/RECHAZADO/ANULADO, raw response for audits). Webpay: `pago_webpay_iniciar_view` creates the transaction and renders an auto-submitting form (Transbank's protocol needs a POST of `token_ws` to their URL, not a plain redirect); `pago_webpay_retorno_view` accepts both GET and POST for the return (observed live against the sandbox that Transbank's redirect actually arrives as GET with `token_ws` as a query param, despite docs describing POST) and handles all three cases (`token_ws` approved/declined, `TBK_TOKEN` user-cancelled, neither = timeout). Khipu: `pago_khipu_iniciar_view` redirects to Khipu's hosted payment page; `pago_khipu_notificacion_view` is the webhook (never trusts the webhook body — always re-queries Khipu's `/payments/{id}` before marking anything paid, per Khipu's own guidance); `pago_khipu_retorno_view` double-checks on the user's way back too, for UX (in case the webhook hasn't landed yet). **Webpay was verified end-to-end live** against Transbank's public integration sandbox (no merchant account needed — the SDK ships public test credentials) — a real approved transaction was completed via the actual bank-simulator pages and the `Contratacion` correctly advanced to EN_CURSO. **Khipu could not be tested** — unlike Transbank, Khipu has no public sandbox; it requires a real account (`KHIPU_API_KEY` from khipu.com's dashboard) that only the project owner can create. Without it, `KhipuService` raises a clear `RuntimeError` instead of failing silently or crashing with a 500.

Getting there needed three fixes beyond just retrying the download:
  1. **C++ toolchain / dlib**: real `dlib` has no prebuilt wheel for Python 3.14 and its `CMakeLists.txt` refuses any compiler but MSVC on Windows. The first pass installed Visual Studio Build Tools 2022 (`Microsoft.VisualStudio.Workload.VCTools` + `--includeRecommended`, silently via the `vs_buildtools.exe` bootstrapper from `aka.ms/vs/17/release/vs_buildtools.exe`) to compile it from source, and that worked — but **this was later replaced**: `requirements.txt` now installs `dlib-bin` (an unofficial repackaging with real `cp314-win_amd64` wheels, same `import dlib` module) instead, avoiding the multi-GB Build Tools install entirely. Two follow-on quirks from that swap: pip doesn't recognize `dlib-bin` as satisfying `face_recognition==1.3.0`'s declared `dlib>=19.7` dependency (harmless resolver warning), and `face_recognition` must be installed with `--no-deps` (`pip install face_recognition==1.3.0 --no-deps`) or pip tries to pull real `dlib` anyway — its actual runtime deps (`Click`, `face_recognition_models`) are listed separately in `requirements.txt` to cover for that.
  2. **NumPy ABI mismatch**: `requirements.txt` pinned `opencv-python==4.9.0.80` (the version the thesis originally used), but that build is compiled against the NumPy 1.x ABI and crashes with `AttributeError: _ARRAY_API not found` under NumPy 2.x — and NumPy 1.x has no wheel for Python 3.14, so downgrading NumPy isn't an option. Fix: upgraded to `opencv-python>=4.10` (first line with NumPy-2-compatible wheels for `cp314`); `requirements.txt` updated to match.
  3. **`pkg_resources` removed**: `face_recognition_models` (a `face_recognition` dependency) still calls `pkg_resources.resource_filename()` to locate its `.dat` model files; `setuptools>=81` deleted `pkg_resources` outright (previously just deprecated). Fix: pinned `setuptools<81` in `requirements.txt` (still emits a deprecation warning on import, but works).

That first-attempt miss is a real, useful signal: a naturally-timed blink doesn't always land inside a fixed ~2s window, so if this becomes a recurring complaint, the first place to adjust is `DURACION_CAPTURA_MS` in `_captura_camara.html`'s JS (longer window) and/or `FRAMES_MIN_PARPADEO`/`INTERVALO_FRAME_MS`, not the EAR/quality thresholds — those worked correctly both times.

  **Low light was then tested too, live, and surfaced a real, serious bug — not in the rejection logic, in performance.** Frames were darkened at the pixel level via a `CanvasRenderingContext2D.prototype.drawImage` filter patch injected into the live page (brightness ×0.08) so the *real* webcam capture, quality gate, and face detector all ran unmodified against genuinely dark frames — not a synthetic test image. First run: `/ajax/validar-captura-rostro/` correctly rejected it in the end ("No se detectó tu rostro con claridad... con buena luz") — but took **~13.5 minutes**, and other requests hitting the same dev server (the `/ajax/mensajes-no-leidos/` poll, normally every 15s) queued up in bursts the whole time, meaning the server was effectively stalled for everyone, not just this request. Root cause: `_detectar_rostro_unico` used to retry with `face_recognition`'s `model='cnn'` (a much heavier neural detector, no GPU here) whenever the fast HOG detector found nothing — and in low light HOG fails on nearly every frame of the burst, so the expensive CNN path fired ~16-20 times in a row. **Fixed**: removed the CNN fallback entirely (HOG only — no longer needed now that this is a frontal-only blink flow, not the old head-turn design, and there's enough frame redundancy to tolerate HOG missing a few), and reordered `verificar_prueba_de_vida_parpadeo` to run `_calidad_de_imagen_aceptable` (brightness/blur, cheap) *before* attempting face detection per frame instead of after, so a dark frame gets discarded near-instantly instead of paying for detection first. Re-tested live with the identical darkening patch afterward: same correct rejection, now in a few seconds, with no queuing of other requests. `manage.py test KeyServApp` (134 tests) still passes clean after this change. Still untested: a genuine mismatch case (a different person's face correctly rejected) and whether `BRILLO_MINIMO`/`NITIDEZ_MINIMA`/`TOLERANCIA_COMPARACION = 0.5` are well-calibrated outside the one lighting condition tested so far. Also worth keeping in mind for real deployment (not yet addressed): this endpoint still does the CV work synchronously inside the request/response cycle on Django's single dev server — fine now that per-request cost is low, but real production traffic will want this behind a multi-worker WSGI server (gunicorn/uwsgi) at minimum, since face detection is still CPU-bound work per request even without the CNN fallback.
